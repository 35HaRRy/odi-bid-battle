# Account API deployment

Deploy identity, ownership/API gate, UI and migration together in a maintenance window, after an approved backup and restore rehearsal. Never reopen an unauthenticated old API after migration. Passing local checks is not authorization to deploy.

## Configuration (standalone and Vercel)

### Local development upgrades

`pnpm dev` starts PostgreSQL and the API/web processes. Docker's schema initialization runs only when the database is first created: an existing `db/data` volume is **not** upgraded by restarting Docker. Before running a newer account-enabled API against the older Compose database, back it up, then run `pnpm db:migrate` from the repository root. This command targets Compose's `bidbattle` database, not a custom `DATABASE_URL`; for a custom target, apply `db/schema.sql` using that target's approved connection. The existing transactional schema preserves legacy records. Legacy content retains its reserved disabled owner; registering a new account does not claim it. Never delete `db/data` to fix missing tables.

The standalone API's development command loads `api/.env`. Keep `APP_URL` and `ALLOWED_ORIGIN` aligned with the actual frontend URL (normally `http://localhost:5173`). Complete SMTP/Google settings advertise configured capabilities, not provider health. A successful `/health` or `/auth/session` alone does not prove the authentication schema exists.

If registration fails after migration, verify the SMTP connection/authentication privately. Nodemailer `EAUTH` with SMTP `535` means the provider rejected authentication: correct `SMTP_USER`/`SMTP_PASS` and provider requirements (for example, a provider-issued app password). Do not print these values or bypass email verification. Restart the API after changing `api/.env`. Google login must return a 302 from `/auth/google/start` before testing consent/callback with an approved Google test account.

- Node 24; existing PostgreSQL pool. `DATABASE_URL` is injected privately, never printed.
- `APP_URL`: fixed frontend origin, e.g. `https://app.example.test`. Links always target `/account/verify-email#token=…` or `/account/reset-password#token=…`; never request Host. The UI immediately removes fragments from browser history and submits tokens via POST. Preserve `Referrer-Policy: no-referrer` on account/token pages in frontend hosting headers. Never log request bodies, cookies, token fragments or links. API responses already set no-referrer and no-store.
- `ALLOWED_ORIGIN`: exactly one frontend origin, no trailing slash/path. Both URLs are mandatory and HTTPS-only with `NODE_ENV=production`. Development defaults to `http://localhost:5173`; credentials-enabled CORS permits only this configured origin. The production frontend/API must be same-site (prefer same origin `/api`); SameSite=Lax does not support cross-site cookie deployment.
- `TRUSTED_PROXIES`: empty by default; client IP is the socket address. Only explicit trusted proxy IPs/CIDRs are accepted, comma-separated. No `true`, hop counts or wildcard trust. Configure only known controlled proxies that overwrite forwarded headers, and prevent direct access around them. Verify the Vercel ingress contract/IP ranges before enabling trust; otherwise limits intentionally share the ingress IP rather than trust spoofable headers. This may constrain all users behind a proxy until configured.
- `SMTP_HOST`, `SMTP_PORT` (1–65535), `SMTP_SECURE` (`true` for implicit TLS, usually 465; `false` for required STARTTLS, usually 587), `SMTP_FROM`; optional `SMTP_USER` and `SMTP_PASS` must be configured together. TLS certificate validation stays enabled, SMTP debugging/logging stays disabled. Incomplete config makes mail routes return generic retryable 503; there is no console-link fallback. Preflight SMTP connection/auth verification happens before account-specific work. Only SMTP recipient acceptance counts as delivery success; this does not promise inbox delivery.
- Verify serverless outbound DNS/TCP/SMTP connectivity, provider restrictions, sender authorization, SPF/DKIM/DMARC and function timeouts. Every send and verify is awaited; no detached serverless background sends. SMTP connection/greeting timeout is 10 seconds, socket timeout 15 seconds. Budget for preflight plus delivery (provisioning sends two messages).

`buildApp(store, options?: AppOptions)` exports injectable validated config and `AccountMailer` for tests; neither auth nor CSRF can be disabled. Both runtime entry points explicitly load the same config. No real SMTP/Google or production migration was exercised during development.

## HTTP and security contracts

`GET /auth/session` and successful login return `{user:null|{id,username,email},csrfToken,googleEnabled,mailEnabled}`. `googleEnabled` means complete validated Google configuration is present, not a network health probe. `mailEnabled` means a valid SMTP transport/sender is configured, not that an inbox/network health probe succeeded; injected test mailers declare `enabled` explicitly. Bootstrap does not contact either provider. Send credentials/cookies, exact `Origin: ALLOWED_ORIGIN` and `X-CSRF-Token` on **every unsafe request**, including login/register/reset/logout. Cookies are HttpOnly, SameSite=Lax, Path=/; production adds Secure and `__Host-` names. No Domain is set. Duplicate security cookie names fail closed. Never store credentials in localStorage. Session tokens and one-time tokens are stored only as SHA-256 digests.

CSRF values are stable for the lifetime of their cookie, so bootstrapping another tab does not invalidate an existing tab. The server derives the returned token using HMAC-SHA-256 keyed by the opaque HttpOnly cookie secret, with separate `odi:csrf:v1:session` / `odi:csrf:v1:anonymous` domains. A returned CSRF token cannot be used as the session/anonymous cookie. Only the CSRF hash is stored in `auth_sessions`; no raw session or CSRF token is persisted server-side. Anonymous bootstrap reuses its opaque one-hour cookie without extending its expiry; login clears it and issues a fresh seven-day session/token. Logout clears both cookies and revokes the session; password reset revokes all sessions. Bootstrap does not extend session expiry. Tabs surviving a login/logout/reset must explicitly refresh their session view; unsafe operations are never blindly replayed. At this upgrade, reload existing account tabs once: old digest-format anonymous cookies and pre-upgrade random session CSRF views are replaced on bootstrap. No schema/data migration is needed.

All uploaded candidate images (create, catalog edit, list edit, draft edit), battlefield/background images and new team image inputs require the existing PNG/JPEG/GIF/WebP MIME + matching signature policy. HTML/SVG and MIME-spoofed payloads are not uploads. Every binary response family uses `nosniff`, `Cache-Control: no-store` and `Content-Security-Policy: sandbox; default-src 'none'`. Unsupported or signature-mismatched historical assets are returned byte-for-byte as `application/octet-stream` attachments, not executable documents; their database bytes/metadata and historical references are never rewritten or deleted. They may no longer preview inline. The bundled, code-owned default SVG background alone remains an inline SVG, with the same sandbox policy. Preserve these response headers through the deployment proxy/CDN and verify them on GET and HEAD after cutover.

POST endpoints: `/auth/register {username,email,password}` → 202, `/auth/login {login,password}` → SessionView, `/auth/logout` → 204, `/auth/forgot-password {email}` → 202, `/auth/resend-verification {email}` → 202, `/auth/verify-email {token}` → 204, `/auth/reset-password {token,password}` → 204. Passwords are 12–128 characters and never trimmed. Verification expires in 24 hours; reset in 30 minutes. Wrong/expired/reused links return generic 400. Reset revokes all sessions atomically. Unverified/disabled accounts cannot log in. A credential version/hash recheck and session insert share the account lock with password reset.

Login failures share one canonical account budget across username/email aliases (5/15min), plus IP (20/15min). Successful attempts do not consume failure counters, but cannot bypass an exhausted budget. Registration/recovery/resend each use separate account and IP budgets (5/hour); 429 carries Retry-After. Rate state is shared in PostgreSQL. KDF saturation/database failures map to generic retryable 503, never raw errors. Do not log request bodies at the proxy or hosting platform.

Local HTTP login uses `AuthStore.loginLocalUser(login,password,ip)`: a single transaction/client holds consistently ordered account and IP advisory locks through budget admission, credential verification, failure accounting or final session insertion. Concurrent aliases/guesses cannot exceed remaining verification attempts or issue a session after a preceding failure exhausts either budget. Expiry uses database wall-clock time after lock waits; locks release on commit/rollback/connection closure. Calls sharing an account or IP serialize and occupy pool slots while waiting; budget function latency/capacity accordingly. The lower-level `authenticateLocalUser` retains reset-safe session creation but does not apply HTTP rate policy.

To avoid an SMTP-recipient-rejection account oracle, unknown/disabled recovery recipients, already-verified resend recipients and duplicate registration recipients receive the same kind of message with an unpersisted, unusable token. This is deliberately rate-limited; response status and SMTP failures do not disclose account existence. Receiving an email does not mean an account exists. No account/token is created by those dummy deliveries. Failed delivery rolls back newly created accounts/tokens; retry is safe. SMTP and PostgreSQL are not a distributed transaction: a message accepted immediately before a DB commit failure may contain an unusable link; retry through the form.

Public account routes and CSRF/session middleware are mounted **before** the mandatory domain gate. The gate uses `res.locals.user` as the actor, rejects unauthenticated domain access with 401, and leaves account/health routes public; do not move account routes behind the gate. Root repositories fail closed without an explicit user scope.

## Google OIDC provisioning and browser contract

Create a Google OAuth **Web application** client in the operator-controlled project. Supply `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` and `AUTH_STATE_ENCRYPTION_KEY` privately to both runtime entry points. All four absent disables Google; partial/invalid configuration fails startup rather than advertising a broken capability. No provider secret or key belongs in frontend environment variables, source, logs or a committed `.env`.

Register the exact externally visible callback, with no query, fragment or trailing slash:

- Standalone API/local development: `http://localhost:3001/auth/google/callback`.
- Production Vercel same-origin `/api` deployment: `https://app.example.test/api/auth/google/callback`; replace `app.example.test` with the approved `APP_URL` host **in both Google and GOOGLE_REDIRECT_URI**.
- A same-origin reverse proxy without `/api` may use `https://app.example.test/auth/google/callback`. Production callback origin must equal `APP_URL`; HTTPS is mandatory. Do not derive callbacks from incoming Host/forwarded headers. Local frontend remains `http://localhost:5173`.

Provision a cryptographically random **32-byte key encoded as standard padded base64** (44 characters) in the secret manager as `AUTH_STATE_ENCRYPTION_KEY`. All active instances must share it. AES-256-GCM encrypts the recoverable PKCE verifier with a fresh IV and state-hash authenticated context. State and transaction-cookie values are stored only as SHA-256 digests; nonce and validated return path are not credentials. OAuth rows expire after 10 minutes and are deleted on consumption/expiry cleanup. Rotation invalidates in-flight OAuth transactions only; restart sign-in after rotation. Coordinate rotation across instances (drain/restart together); there is deliberately no old-key fallback. Existing 7-day app sessions and issuer/subject identities survive. Client-secret rotation may also interrupt in-flight exchanges: follow the provider's overlap procedure and restart failed sign-ins. Do not rotate the state key with every deployment.

`GET /auth/google/start?returnTo=/same-origin/path` starts **login only** and responds 302 to Google. Authenticated users must use explicit linking instead (409). Request only `openid email profile`, authorization code, nonce and S256 PKCE; no offline access or persistent Google tokens. The short-lived browser transaction cookie is `odi_google_tx` locally, `__Host-odi_google_tx` in production, with the shared HttpOnly/SameSite=Lax/Path=/ cookie policy. Starting again in the same browser replaces that cookie, so only the latest flow can complete. Shared PostgreSQL start budgets are 20/15min by trusted IP and, for linking, user ID; 429 includes Retry-After.

For linking, bootstrap the session/CSRF, then `POST /auth/reauthenticate {password}` (204), followed within **five minutes** by `POST /auth/google/link {returnTo?:"/account"}`. Both require the current session, exact Origin and CSRF. Reauthentication verifies the untrimmed local password under the reset-safe credential/session locks and shares local-login failure budgets; it neither issues nor extends a session. Linking returns `{url}` (200); navigate to it at the top level. The callback requires the **same original session**, a still-recent local reauthentication, a valid browser transaction and a unique Google issuer/subject. It cannot replace another linked identity or link one owned by someone else. Google-only relinking is not supported; a Google-only account can establish a local password through the existing reset flow first.

The callback consumes state atomically **before** any exchange; failures/replay cannot reuse it. `openid-client` validates issuer, audience, expiry, nonce and PKCE exchange, with explicit non-repudiation checks to cryptographically verify ID-token signatures through Google's JWKS. Userinfo must match the validated subject and verified email. Persist only issuer/subject/user mapping, never access/refresh/ID tokens. A matching email without an existing issuer/subject mapping returns 409 with an instruction to sign in locally and link explicitly; it never merges accounts. New Google users get a random valid unique username and a verified account; existing identities remain keyed by issuer/subject even if Google changes their email. Their app email is not silently changed.

Successful callbacks redirect to a validated same-origin path on `APP_URL` (default `/`); malformed/external paths fall back to `/`. Login sets the shared seven-day app session cookie; linking preserves its session. Bootstrap `/auth/session` again after the redirect to obtain the CSRF token. Callback errors are generic JSON 400/403/409; do not log callback query strings/codes/state, cookies, provider responses or secrets at proxy/platform level. Transient failures require restarting the flow. Real Google consent/redirect/cookie behavior must still be checked by the operator against approved test accounts after secret provisioning; only fake-protocol tests were run here.

## Operator legacy claim

After approval/backup/migration, privately supply `DATABASE_URL`, `LEGACY_ACCOUNT_EMAIL`, APP_URL/ALLOWED_ORIGIN and SMTP variables. Run with Node 24:

```text
pnpm --filter odi-bid-battle-api run provision-legacy --confirm-legacy-claim
```

No password, token, URL or recipient is emitted to stdout/stderr. The command preflights SMTP then holds the reserved legacy account row lock through email assignment, expiring verification/reset-token creation and both SMTP acceptances. Failure rolls back email assignment/new tokens; old invitation tokens remain valid after a failed retry. A successful same-recipient retry while pending replaces outstanding tokens. Different recipients and completed claims are rejected under the lock (including concurrent claims); unique email constraints remain enforced. There is no HTTP claim endpoint or administrator privilege.

The legacy account remains disabled until **both** the verification link and password-setup/reset link are consumed, in either order. Verification alone never creates a session. Ordinary recovery cannot activate the disabled legacy account; use the operator command to reissue expired pending invitations. After activation, normal recovery works. If one SMTP message was accepted but the second fails, rollback invalidates the accepted link; rerun with the same approved recipient. The operator must check approval/recipient out of band and should avoid concurrent duplicate command invocation. Never run this against a real database without explicit approval.

## Maintenance-window runbook

1. Obtain explicit approval, identify the database and legacy recipient out of band, and schedule downtime. Stop writes and disable **all** old API entry points, deployment aliases, preview URLs and direct origin access. A maintenance page must not proxy the old API.
2. Take an encrypted PostgreSQL backup with the operator's existing tooling and privately injected connection. Include bytea images, preparation JSON, teams, live balances/history, and the schema. Restore it into a separately authorized disposable database; verify counts and representative image/history bytes before rehearsing `db/schema.sql` there with `psql -v ON_ERROR_STOP=1`. Never use a real database for development tests.
3. Rehearse the migration twice. Verify one disabled, passwordless legacy owner; existing library roots public, historical auctions private; unchanged preparation locks, overrides, images and references. Confirm a new private user's ownership/visibility survives the second run. The schema is transactional; any SQL failure must stop cutover, not continue with a partially configured app.
4. During the approved window apply that same schema to the backed-up target, using an explicit operator connection, not an HTTP request. Neither entry point runs migration/provisioning automatically. Deploy matching API/UI together, inject secrets privately, then run the legacy invitation command only for the approved recipient.
5. Before reopening: verify anonymous private JSON/images return 401, foreign private IDs return 404, unsafe requests without Origin/CSRF fail, authenticated JSON/images carry `Cache-Control: no-store`, secure host-only cookies are set, account pages have no-referrer, and `/api/*` rewrites precede SPA fallbacks. Disable CDN/service-worker caching of private responses. Check `/app`/account refresh and Google callback routing on the actual host; local checks cannot validate the hosting ingress.
6. On failure keep maintenance mode. Restore only through the approved recovery process and reconcile writes made since backup. Never roll back to an externally reachable unauthenticated API, even if the old UI works. Close obsolete deployments before ending maintenance.

Transport TLS, at-rest encryption, backup retention/access and actual trusted proxy ranges are operator checks. Test HTTPS redirects and CORS with an untrusted origin. Rotate database/SMTP/client secrets through the secret manager, drain old instances and verify old credentials are rejected; never expose them as `VITE_*`. State-key rotation behavior is described above.

## Resource limits and expiry maintenance

Node 24.22.2 local measurements (not a serverless capacity promise): three fresh processes, 30 warm samples, median **64 ms** (56–98 ms); wrong-password median **64 ms**, unknown-account median **60 ms**; two active jobs **132–133 MiB peak RSS** (baseline 67 MiB, single-job peak 100–101 MiB). The KDF has bounded concurrency and rejects saturation with retryable 503. Measure latency, RSS, pool occupancy and cold starts on the intended deployment before choosing instance memory/concurrency; queued same-account/IP login attempts also occupy connections. Do not lower hash cost to conceal capacity failures. Existing hashes retain versioned cost parameters.

Sessions expire after 7 days, reset links after 30 minutes, verification links after 24 hours, OAuth transactions after 10 minutes. Validity is enforced at use time independently of cleanup. OAuth/rate rows have opportunistic cleanup, but sessions and consumed/expired email tokens need operator-scheduled pruning. Run small bounded transactions against the approved target, for example delete at most 1,000 expired sessions or expired/consumed tokens per transaction using a primary-key subquery with `FOR UPDATE SKIP LOCKED`; repeat with pauses outside peak traffic. Do not delete unexpired, unconsumed invitations. Rate/OAuth pruning can use the same bounded pattern on their hash primary keys.

If pruning fails, expiry still denies access; table/index growth, backup size and query latency increase. Alert on cleanup failures and row counts, retain no token/cookie/request-body logs, and retry the operator job rather than extending expiry or bypassing checks. If a verification/reset token is lost or expires, resend/recover; pending disabled legacy invitations require the provisioning command. SMTP acceptance followed by a failed database commit remains an unusable-link/retry failure mode, not successful activation.

## Test fixtures and release evidence

API integration tests require an explicitly disposable database (`AUTH_TEST_DATABASE_URL` for isolated auth schemas; `DATABASE_URL` for domain tests). Apply the schema only there. Use UTF-8/template0 when the local cluster default is not UTF-8. `api/test/helpers/auth.ts` creates synthetic verified users through the real password hasher and logs in via HTTP cookies/CSRF; it is never imported by runtime entry points. Tests close their servers/pools and drop their owned schemas; the external runner must drop its owned random database even after failure.

Browser fixtures may inject `AccountMailer` into `buildApp` to capture synthetic links locally. They must live outside shipped code, never add a production bypass or print links, and must use actual React, Express, PostgreSQL, login cookies and token endpoints. OIDC protocol tests use the real `openid-client` validator with local signed responses, not live Google consent. Controlled mail capture is not SMTP/inbox verification. Live SMTP, Google, deployed HTTPS/proxy/cache headers and deployment resource sizing remain operator release gates.

For no-secret local checks use explicit Vite/Vitest configuration with `envDir:false` and `configFile:false` for programmatic Vite builds; do not let tooling implicitly load application `.env` files. Supply a public same-origin `/api` frontend build value explicitly. Never stage real `.env`, test database credentials, captured mail links, cookies, build output or browser traces.
